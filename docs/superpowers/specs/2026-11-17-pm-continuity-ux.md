# 專案經理對話的銜接與「從哪裡繼續」— 改善提案

- 日期：2026-11-17
- 狀態：提案（只研究，未改任何程式碼）
- 資料來源：`server/data/store.db` 唯讀查詢（2026-11-17 快照）＋ `http://localhost:5190/api/*` 實測 ＋ 讀元件原始碼
- 限制說明：畫面部分是讀元件程式碼與打 API 得出的，**沒有實際開瀏覽器逐頁點過**；凡是推測都會標「推測」。DB 時間戳一律是 UTC。

---

## 0. 一頁結論

使用者的痛點由三個各自獨立、都很小的原因疊出來：

1. **按鈕的行為就是「每按一次開一場新的」**，而且分頁不會保存，重新整理或切工作區後原本那場就從畫面上消失，只能再按一次按鈕 → 又一場新的。
2. **自動命名對專案經理從來沒生效**，原因是一行字串比對：預設標題是「👨‍💼 專案經理」，但命名器拿來比對的是 agent 檔名「智能體編排者」，對不上就當成「使用者自訂標題」跳過。19 場互動式 PM 對話裡 18 場至今沒有標題。
3. **歷史面板沒有顯示任何能辨識的東西**（最後一句、訊息數其實 API 都有回傳，前端沒用），而且被排程執行紀錄洗版（兩個主要工作區的歷史裡 70% 是 `[排程 …]`）。

最划算的做法是先修這三個（合計約 1.5–2.5 個工作天），用一兩週，再決定要不要做需要 LLM 的「狀態判斷」和「交接摘要」。後兩者有價值，但準確度有不確定性，不該先做。

## 1. 現況診斷

### 1.1 為什麼一直出現新紀錄

| 行為 | 程式碼位置 | 說明 |
|---|---|---|
| 「找專案經理討論」每按一次就開新 session | `client/src/App.tsx:256-260` | 直接 `api.startOrchestrator()`，完全不看這個工作區有沒有上一場 |
| 總管簡報「展開討論」也是每次開新的 | `client/src/App.tsx:264-276` | 開新 session 後把 `discussSeed` 當第一句送出 |
| 指令面板的「找專案經理討論」同上 | `client/src/components/CommandPalette.tsx:63` | 接的是同一個 `askOrchestrator` |
| session 在「按下去那一刻」就建立，不是送出第一句時 | `server/src/routes/sessions.ts:368-375` | 所以誤按也會留下空殼 |
| 分頁只存在 React state，沒有寫進 localStorage | `client/src/App.tsx:120` | 重新整理頁面 → 分頁全沒了 |
| 切工作區會清空所有分頁 | `client/src/App.tsx:216-220`、`client/src/components/WorkspaceSwitcher.tsx:35` | 切回來時原本那場不會回來 |

分頁一旦消失，要回到原本那場只有兩條路：去歷史面板裡找（見 1.2，找不到），或再按一次按鈕（又開一場）。使用者實際上選了後者。

**數字（全部 85 筆 PM session 的組成）：**

| 類別 | 筆數 | 備註 |
|---|---|---|
| 排程執行 `[排程 …]` | 40 | LP audio 20、個人IP 20 |
| 互動式對話（使用者自己開的） | 19 | 本提案的主角 |
| 空殼（0 則訊息） | 14 | 按了按鈕沒講話；歷史面板已過濾，但佔了 16% |
| `(復原) …` | 9 | 6/2 事故復原產物，都在預設工作區 |
| 工作區設定顧問 | 3 | 同一個 agent id，不同標題 |

19 場互動式對話的長度（以使用者訊息數計）：1, 1, 1, 1, 1, 1, 1, 2, 4, 5, 6, 10, 11, 17, 18, 26, 27, 30, 31。

- 中位數是 5 則，但分佈是兩極的：**7 場（37%）只講了一句就丟下**，另外 9 場是 10 則以上的長談。
- 那 7 場「一句就丟」不是誤按，多數是**想接續卻開到新的**。19 場裡有 **6 場的第一句話就是在請 PM 回想上次**：
  - 5/9「你幫我跟進一下智能體編排者那邊的對話，我現在卡在…」
  - 5/29「找一下我們之前有中斷的話題，我們等等接續吧」
  - 6/18「還記得我們之前聊過要買 audioscape…的話題嗎?」
  - 6/27 15:04「可以幫我看看目前記錄下來還沒做完的項目有哪些嗎?」
  - 6/27 15:18「幫我看一下我們之前中斷的項目…」
  - 7/16「昨天我們中斷了一個對話，你先核對一下昨天中斷的內容…」
- 6/27 那兩場相隔 14 分鐘、問的是同一件事，得到兩個不同答案：第一場回「目前沒有正式的待辦清單」，第二場列出「5 條中斷項目」。這說明「上次停在哪」現在沒有固定來源，全看 PM 當下翻到哪份記憶。
- 7/16 那場只有 4 則訊息就停了，而它要接續的 7/13–7/15 那場有 102 則訊息——原本那場明明還在，只是使用者找不到。

### 1.2 為什麼歷史看不出是哪一場

歷史卡片（`client/src/components/HistoryPanel.tsx:196-227`）只畫三樣東西：`s.title`（:209）、agent 名稱與相對時間（:215-216）。對 PM 來說就是：

```
● 👨‍💼 專案經理
  智能體編排者 · 3 天前
```

這正是使用者描述的「只標『專案經理』『智能體編排者』和上次時間」。

其實 `GET /api/sessions` 已經回傳 `messageCount`、`lastSnippet`、`lastRole`（`server/src/store/sessions.ts:47-69`），前端完全沒用。實測 LP audio 的回應是 **108 KB，其中 94 KB 是沒被顯示的 `lastSnippet` 全文**，而歷史面板每 5 秒輪詢一次（`HistoryPanel.tsx:60`）。

另外兩個讓人更難找的因素：

- **排程洗版**：LP audio 歷史 33 筆裡 20 筆是 `[排程 …]`（61%），個人IP 24 筆裡 20 筆（83%）。兩個工作區合計 57 筆有 40 筆（70%）是排程，使用者自己的對話被擠在中間。
- **對話視窗的標頭也沒有標題**：`client/src/components/ChatWindow.tsx:274-287` 顯示的是 agent 名稱加 `session: 7b47d7f1` 這種 8 碼 id。後端有改標題的 API（`sessions.ts:121-137`），但畫面上沒有入口。

### 1.3 自動命名的實際狀況：有觸發，但被判斷式擋掉

結論：**不是沒觸發、不是格式問題、也不是前端沒用到 title，是「預設標題」的判斷式對 PM 永遠不成立。**

- 觸發點正常：每回合結束都會呼叫（`server/src/agentManager.ts:836`）。
- 擋下來的地方在 `server/src/autoTitler.ts:31-40`：

  ```ts
  const agentDisplayName = agent?.name || rec.agentId;   // PM 的值是「智能體編排者」
  const looksLikeDefault =
    rec.title === `${rec.agentId} 對話` ||
    rec.title === agentDisplayName ||                     // 「👨‍💼 專案經理」≠「智能體編排者」
    rec.title.endsWith(" 對話");
  if (!looksLikeDefault) { /* log "custom title" 然後 return */ }
  ```

  PM session 建立時標題寫死是 `"👨‍💼 專案經理"`（`sessions.ts:373`），而 agent 定義檔 `~/.claude/agents/agents-orchestrator.md` 的 `name` 是「智能體編排者」。三個條件都不成立，於是被當成使用者自訂標題跳過。

- 資料佐證：19 場互動式 PM 對話中，**18 場標題仍是「👨‍💼 專案經理」**，只有 1 場有標題（「新人自媒體啟動三週衝刺規劃」，4/30 建立，也是唯一有 tag 的一場）。那一場沒有現在會加的 agent 名稱前綴，推測是命名邏輯改版前產生的。
- 同一套「是不是預設標題」的判斷另外抄了兩份，一樣對 PM 失效：`client/src/App.tsx:341-344`、`client/src/components/AgentMeetingRoom.tsx:59-60`。
- 就算修好，命名只看前 4 則訊息（`autoTitler.ts:45`），而且只在第一次嘗試（`attempted` 是記憶體內的 Set）。對長談來說標題反映的是「開場在聊什麼」，不是「後來停在哪」——所以光有標題不夠，還需要「最後一句」。

### 1.4 目前的跨對話記憶：有，但使用者看不到，也不穩

新開的 PM 並不是失憶的。系統會注入兩層記憶（`agentManager.ts:468-482`）：工作區記憶與「同事記憶」。同事記憶在 session 閒置 30 分鐘被回收時自動蒸餾（`agentManager.ts:348-362`、`server/src/memoryDistiller.ts:148-177`），用快速模型**整份取代**舊版。

三個問題：

1. **使用者看不到**。它只存在 system prompt 裡，使用者要知道 PM 記得什麼，只能開一場新的去問（這就是 1.1 那 6 場的來源）。
2. **會被排程執行蓋掉**。目前 LP audio 與個人IP 兩個工作區的 PM 同事記憶，`distilled_from_session_id` 都指向 `[排程 …]` 那場。LP audio 那份 3,582 字裡大半是每週競品行情的數字；使用者手上那件事（M83421 電容定價，卡在外殼公差照片）只剩最後一小段。蒸餾提示（`memoryDistiller.ts:64-83`）沒有保留「使用者進行中事項」的固定區塊。
3. **有 30 分鐘空窗**。上一場還沒被回收前就開新的，新的那場拿到的是舊版記憶。6/27 的時間點（上一場最後訊息 14:33，新場 15:04）跟這個空窗吻合，但沒有 log 可以證實，只能列為可能原因。

## 2. 改善方案

工作量：小 = 半天到一天；中 = 一到三天；大 = 三天以上。皆含測試。

### 方案 A　讓每場對話認得出來（修命名 + 歷史卡片）— 小

**使用者看到什麼**

```
● M83421 電容定價：1% 還是 10%                     6 則
  停在 [PM]：兩套定價表都備好了，照片到了直接選表…
  專案經理 · 15 天前
  ──────────────────────────────────────────────
  ☐ 顯示排程執行（20）
```

- 歷史卡片：標題、最後一句（2 行截斷，標明是你說的還是 PM 說的）、訊息數、時間。
- 排程執行預設收起來，勾選才顯示。
- 對話視窗標頭顯示標題，點一下可以改名。

**要改的檔案**

| 檔案 | 改什麼 |
|---|---|
| `server/src/autoTitler.ts:31-40` | 把 PM 的預設標題（`👨‍💼 專案經理`）納入 `looksLikeDefault`。建議把「預設標題判斷」抽成一個共用函式，取代散在三處的複本 |
| `server/src/autoTitler.ts:83-85` | PM 的標題不要加「智能體編排者 · 」前綴（見 3.1 命名不一致） |
| `server/src/routes/sessions.ts:63-73` | `lastSnippet` 截到 200 字再回傳（108 KB → 推估 15 KB 上下） |
| `client/src/components/HistoryPanel.tsx:196-227` | 卡片加最後一句、訊息數；加「顯示排程執行」開關，預設關 |
| `client/src/components/ChatWindow.tsx:274-287` | 標頭把 `session: xxxxxxxx` 換成標題，可點擊改名（呼叫既有的 PATCH） |
| `client/src/App.tsx:341-344`、`AgentMeetingRoom.tsx:59-60` | 改用共用的預設標題判斷 |
| 一次性腳本 | 幫既有 18 場補標題（18 次快速模型呼叫）。補標題時建議餵「前 2 則 + 最後 2 則」，長談才不會只反映開場 |

**資料欄位**：不用加。

**風險**

- 低。命名器每場多一次快速模型呼叫；以目前 6.5 個月 19 場互動對話的量，成本可忽略。
- 標題是模型產生的，偶爾會下得不準；所以要有改名入口，而且卡片上的「最後一句」是不靠模型的原文，兩者互補。
- 修好後，既有 18 場裡還開著的會在下一回合自動命名；已關閉的要靠補標題腳本。

### 方案 B　預設接續上次，而不是開新的 — 小到中

**使用者看到什麼**

側欄按鈕從一顆變成上下兩列：

```
┌──────────────────────────────────────┐
│ 👨‍💼 繼續：M83421 電容定價              │
│    15 天前 · 6 則                      │
├──────────────────────────────────────┤
│ ＋ 開新話題                            │
└──────────────────────────────────────┘
```

- 這個工作區有上一場互動式 PM 對話 → 主按鈕是「繼續：〈標題〉」，按下去直接回到那一場（走既有的 `openHistorySession`，後端 `--resume` 無感恢復）。
- 沒有上一場 → 維持現在的「找專案經理討論」。
- 「＋ 開新話題」永遠在，按了才開新的。

**何時該開新的**：不做自動判斷，讓使用者自己選，但給足資訊。理由是資料顯示沒有可靠的自動規則——同一個工作區有人隔 3 天接續同一件事，也有人隔天換話題。唯一建議加的提示是：上一場超過約 150 則訊息時，在「繼續」下方加一行小字「這場已經很長，建議開新話題」。150 是估的，上線後看實際狀況調。

為什麼不乾脆「一個工作區永遠只有一場」：現有 4 場超過 100 則訊息（最長 212 則）。永遠接同一場代表每次都要載入整段脈絡，會更快撞到訂閱的用量上限（8/11 的交辦紀錄裡已經出現過 `You've hit your session limit`）。

**同時要做的兩件小事**

1. **分頁保存**：把開著的分頁依工作區存進 localStorage（`agency:tabs:<工作區id>`），重新整理或切回工作區時還原。這樣切工作區不再等於「關掉所有對話」，`WorkspaceSwitcher.tsx:35` 的確認視窗可以拿掉。
2. **總管簡報「展開討論」不重複開**：開新場時把標題預設成簡報項目的標題；同工作區若已有同標題的場次就直接回到那一場。目前同一個簡報項目每天都會出現，每按一次就多一場（11/2、11/17 各一場就是這樣來的）。

**要改的檔案**

| 檔案 | 改什麼 |
|---|---|
| `client/src/App.tsx:256-276` | `askOrchestrator` 拆成「繼續最近一場」與「開新話題」；`onCockpitDiscuss` 加同標題比對 |
| `client/src/App.tsx:120, 216-220` | 分頁寫入／還原 localStorage；還原時用 `/api/sessions` 驗證該場還存在 |
| `client/src/components/AgentSidebar.tsx:171-180` | 按鈕改兩列 |
| `client/src/components/CommandPalette.tsx:63` | 指令面板對應加一項「繼續上一場」 |
| `server/src/routes/sessions.ts:368-375` | `POST /orchestrator` 接受選填的 `title` |
| `client/src/components/WorkspaceSwitcher.tsx:35` | 拿掉確認視窗 |

「最近一場互動式 PM 對話」的定義：同工作區、`agentId = agents-orchestrator`、訊息數 > 0、標題不以 `[排程`、`[批次`、`[workflow`、`🤖 工作區設定顧問`、`(復原)`、`🤝 受派諮詢`、`🛠️ 外包執行` 開頭。前端 `App.tsx:202` 本來就會抓 `/api/sessions`，直接從那份資料挑即可，不用新 API。

**資料欄位**：不用加。靠標題前綴排除排程不夠乾淨，但現有程式已經用同樣手法（`sessions.ts:53`），先沿用；若之後做方案 C 要加欄位，可以順手加一個 `kind`。

**風險**

- 接續一場很舊、很長的對話，回應會比較慢也比較耗用量。用上面那行提示緩解，不擋。
- 還原分頁時遇到已刪除的 session：還原前先比對，查無就丟掉。
- 既有的 `AgentSidebar.test.tsx` 需要跟著改。

### 方案 C　每場對話的狀態與「停在哪」— 中

**先講清楚限制**：使用者想要的「進行中／卡住等你回／已完成」，**無法從現有資料直接算出來**。所有 PM 對話的最後一則都是 PM 說的（可見場次裡 `lastRole = user` 的是 0），所以「最後誰講話」分不出「等你回」和「講完了」。

因此分兩層做：

**C1（不靠模型，確定的訊號）— 小，建議跟方案 E 一起做**

| 狀態 | 判斷依據 |
|---|---|
| 🟡 執行中 | `agentManager.liveStatus` 是 busy／starting，或這場有 `delegations` 還在跑 |
| 🔴 等你批准 | 這場有 `pending_actions.status = 'pending'` |
| ⚪ 已結束 | 使用者手動按「標記完成」 |
| （無標記） | 其他一律不標，只顯示「最後一句」與時間 |

**C2（靠模型）— 中，建議先不做，等 A/B/E 用過再決定**

閒置回收時（跟同事記憶蒸餾同一個掛點，`agentManager.ts:348-362`）多跑一次快速模型，產出：

```
STOPPED_AT: 一句話，60 字內，停在哪、下一步是誰的
STATE: open | waiting_user | done
```

存進 session，卡片上顯示「停在：…」取代原文最後一句。

- **資料欄位**：`sessions` 加 `stopped_at TEXT`、`state TEXT`、`state_source TEXT`（`auto`／`manual`，手動的不被自動覆蓋）、`digest_at INTEGER`。
- **要改的檔案**：`server/src/dbSchema.ts`、`server/src/store/sessions.ts`、新增 `server/src/sessionDigest.ts`（結構照抄 `autoTitler.ts`）、`agentManager.ts` 回收掛點、`routes/sessions.ts` PATCH 支援 `state`、前端卡片。
- **風險**：快速模型判斷「等你回 vs 已完成」一定會有錯。所以它只能是提示，不能拿來自動隱藏或自動封存任何對話，而且必須可以一鍵手動改。排程場次不跑。準確度要上線後抽樣看，現在沒辦法給數字。

### 方案 D　換一場時自動交接 — 中

現有的同事記憶其實已經在做交接，問題是 1.4 列的三點。分兩步：

**D1　保住「使用者進行中事項」不被排程蓋掉 — 小**

改蒸餾提示（`server/src/memoryDistiller.ts:64-83`），規定新版記憶的第一個區塊固定是「## 與使用者進行中的事（停在哪／等誰）」，並明文要求：這場對話沒提到的項目原樣保留，只有使用者明確說做完或不做了才移除。

- 資料欄位：不用加。
- 風險：靠提示約束，快速模型不一定每次都照做。建議加一條後置檢查——舊記憶有這個區塊而新版沒有，就放棄這次蒸餾、保留舊版。這個檢查是純字串比對，可以寫單元測試。

**D2　開新話題時明確帶入上一場重點 — 中，依賴方案 C2**

使用者在方案 B 按「＋ 開新話題」時：

- 新對話頂端出現一張可收合的卡片：「已帶入上一場『M83421 電容定價』的重點：停在…。〔看原對話〕」
- 同一段文字注入新場的 system prompt（`buildOrchestratorSeed`，`sessions.ts:386` 加一個選填的 `handoffFrom` 參數）。
- 上一場還沒被回收、摘要還沒產生時，退而使用上一場最後一則 PM 回覆的截斷版，並在卡片上標明「尚未整理，以下為原文節錄」。

- 要改的檔案：`routes/sessions.ts`（`POST /orchestrator` 收 `handoffFrom`、`buildOrchestratorSeed`）、`App.tsx`、`ChatWindow.tsx`（頂端卡片）。
- 資料欄位：`sessions` 加 `handoff_from TEXT`（指向上一場），卡片才能在重新整理後還在。
- 風險：新話題跟上一場無關時，帶入的內容是雜訊。所以卡片要有「不要帶入」的選項，而且只帶一場，不串接更早的。

**關於「共用工作區層的進行中事項」**：不建議現在另外做一張清單（新資料表 + 讓 PM 吐標記來維護）。理由：目標、成果、專案、看守四個已經做好的「工作區層」功能目前都是 0 筆資料，再加第五個同類功能，被用起來的機率不高。方案 E 的「接續上次」區塊列出未結束的場次與各自停在哪，已經是場次粒度的進行中清單；先看它夠不夠用。

### 方案 E　「從哪裡繼續」的入口 — 小

**使用者看到什麼**

總管簡報是預設首頁，切工作區後也會回到這裡（`App.tsx:123, 218`）。在簡報最上方加一個「接續上次」區塊，只顯示目前工作區的資料：

- 最多列 3 場最近的互動式 PM 對話（排除排程、排除手動標記完成的）。

## 3. 整體操作直觀度

以下是讀過主要畫面後，認為真正影響使用的問題。只列有程式碼或資料根據的。

### 3.1 同一個角色有三個名字

按鈕、分頁、預設標題叫「專案經理」；歷史卡片的 agent 標籤、「按專家」分組、agent 清單叫「智能體編排者」；工作區設定流程用的是同一個 agent id，標題叫「工作區設定顧問」。使用者原話裡同時提到前兩個名字，而自動命名失效的根因也是這個落差（1.3）。

**建議**：前後端各放一個顯示名稱對照（`agents-orchestrator` → 「專案經理」），歷史、分頁、會議室、命名器都走它。agent 定義檔本身不用改。工作量小，可以併入方案 A。

### 3.2 PM 有兩個入口，行為相反

側欄上方的漸層按鈕永遠開新場；在下方 agent 清單點「智能體編排者」則會進會議室，那裡列出過去每一場、有最後一句、可以填主題開新會議——正是使用者想要的東西，但藏在 212 位 agent 的清單裡，而且名字不一樣。

**建議**：方案 B、E 做完後這個問題自然消失；會議室的卡片抽出來共用即可，不需要另外處理。

### 3.3 歷史被排程洗版

數字見 1.2（兩個主要工作區 70% 是排程）。已含在方案 A。

### 3.4 對話視窗看不出自己在哪一場

標頭只有 agent 名稱和 8 碼 session id；分頁上也只有「👨‍💼 專案經理」，同時開兩場 PM 時兩個分頁長得一模一樣（`App.tsx:638-643`，沒有標題時 `topic` 是空的）。已含在方案 A，分頁標題在命名修好後會自動帶出來，但要補一段：命名完成時用 socket 通知前端更新分頁，否則要重開才看得到。

### 3.5 切工作區 = 關掉所有對話

目前切換前會跳確認視窗警告「會關掉目前所有對話 tab」。有三個工作區在輪流用的人，每次切換都在丟失位置。已含在方案 B 的分頁保存。

### 3.6 側欄功能鍵多數通往空面板

側欄有 18 顆功能鍵分四組（預設只展開「經營」那組，`AgentSidebar.tsx:115-121`）。其中目標、成效、看守、筆記、模板、自動接力對應的資料表目前都是 0 筆。這不是錯誤，但「經營」組預設展開的四顆裡，目標和成效兩顆點進去是空的。

**建議**：先不動。這是功能有沒有被用起來的問題，不是版面問題；重排側欄解決不了。等方案 E 上線後，如果「接續上次」區塊成為主要入口，再看哪些鍵可以收起來。

## 4. 建議優先序

### 先做（合計約 1.5–2.5 個工作天）

**第一名：方案 A（修命名 + 歷史卡片 + 排程收合 + 標頭標題），併入 3.1 的名稱對照**

- 直接回應原話「每個專案經理在歷史中都只標…」。
- 根因是一行判斷式，修正範圍小、風險低、不需要新欄位。
- 是後面所有方案的前提：沒有標題，「繼續：〈標題〉」和「接續上次」區塊都沒東西可顯示。

**第二名：方案 B + 方案 E 第一版 + C1（預設接續、分頁保存、首頁「接續上次」區塊、確定訊號的狀態標記）**

- 直接回應原話「我也很難知道我上次處理到一半的是跟哪位專案經理討論」。
- 全部用既有資料，不靠模型判斷，行為可預期。
- 預期效果要講保守一點：它能消掉「為了接續而開新場」這一類（19 場裡至少 6 場），消不掉使用者真的想換話題時開的新場，那本來就該開。

### 用過一兩週再決定

- **D1（蒸餾保留進行中事項）**：小，可以早點做，但要先確認方案 B 上線後，使用者是不是還常常需要靠 PM 的記憶來回想。如果「繼續」按鈕已經讓人直接回到原場，這個需求會變小。
- **C2（模型判斷停在哪／狀態）與 D2（交接卡片）**：兩者綁在一起，合計中到大。價值取決於使用者在有了「繼續」之後還會多常開新話題，現在沒有資料可以判斷。

### 不建議做

| 項目 | 理由 |
|---|---|
| 新增「工作區進行中事項」資料表與 PM 標記協定 | 目標、成果、專案、看守四個同類功能都是 0 筆，先證明場次粒度不夠用再說 |
| 每個工作區強制只有一場 PM 對話 | 已有 4 場超過 100 則訊息，會加速撞用量上限 |
| 用模型判斷的狀態去自動封存或隱藏對話 | 判斷會錯，錯的時候使用者會找不到東西，比現在更糟 |
| 延後到送出第一句才建立 session（消除空殼） | 空殼已被歷史面板過濾，使用者看不到；方案 B 之後誤開的次數也會下降 |
| 重新設計側欄 | 問題在功能使用率，不在版面 |
| 自動合併舊場次、歷史語意搜尋 | 歷史已有全文搜尋；19 場的量用不到 |
